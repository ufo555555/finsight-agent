# 多模态金融研报分析 Agent 设计说明

日期：2026-09-18

状态：已批准

学习基础：Python 基础语法；暂不会 JavaScript/TypeScript

时间预算：每天约 1 小时，预计 12 周完成首版

## 1. 项目定位

项目暂定名为 **FinSight Agent**。用户上传公开公司的年报、公告或研究报告 PDF，并提出一个限定范围的研究问题。系统读取文档中的正文、表格和图表，生成带原文证据、文档页码和不确定性说明的结构化研究报告。

项目用于信息提取、证据组织和风险识别，不预测股价，不生成买入、卖出或仓位建议。

## 2. 设计目标

### 2.1 学习目标

通过项目掌握并亲手实现以下 Agent 能力：

- ReAct/工具调用循环；
- TODO 规划与状态更新；
- 文件系统上下文卸载；
- 子 Agent 委派与上下文隔离；
- 运行检查点和失败恢复；
- 结构化输出与证据约束；
- 人工审批、安全边界和可观测性；
- Agent 离线评测与回归测试；
- 使用 Git 记录、检查、恢复和展示完整开发过程。

### 2.2 产品目标

- 支持一次上传 1–3 份文本型 PDF；
- 抽取正文、页码、表格和内嵌图像；
- 分析业务变化、核心财务指标和风险披露；
- 对选定图表进行趋势理解，并与正文或表格交叉核验；
- 每条重要结论都附可定位的证据；
- 输出 Markdown 报告和机器可读 JSON；
- 保存运行轨迹、耗时、模型调用量和失败信息；
- 提供全 Python 的轻量 Web 界面。

### 2.3 非目标

首版明确不做：

- 实时行情、自动交易或投资组合管理；
- 股价预测和投资建议；
- 全网新闻搜索和无限制网页浏览；
- 扫描件 OCR 的全面兼容；
- 任意复杂图表的精确数值识别；
- 跨数十家公司或多年报表的大规模批处理；
- JavaScript/TypeScript 前端；
- 用户账户、支付和多租户系统。

这些功能只有在核心评测通过后，才进入后续版本候选范围。

`learning-labs/` 用于根据 Deep Agents from Scratch 的 5 个 Notebook 重写关键能力。每个实验只解释一个概念，不追求产品完整度。

`finance-report-agent/` 是独立简历项目。它可以借鉴实验中已经理解的实现，但不直接复制教程 Notebook，也不把 Notebook 当作产品入口。

## 4. 总体架构

首版采用 **3 个 Agent + 确定性工具链**，避免为了“多 Agent”而拆出过多角色。

### 4.1 规划 Agent

职责：

- 判断问题是否属于项目范围；
- 必要时要求用户补充公司、时间范围或分析主题；
- 把问题拆成数量受限的 TODO；
- 为每个 TODO 选择文档、工具和输出要求；
- 控制最大步骤、最大重试和预算。

规划 Agent 不直接编造金融结论。

### 4.2 研究 Agent

职责：

- 检索解析后的正文和表格；
- 按需调用图表理解工具；
- 形成结构化事实和候选结论；
- 为每个候选结论绑定证据；
- 将长工具输出写入文件，只在上下文中保留摘要和引用。

研究 Agent 可以针对相互独立的 TODO 使用隔离上下文并发执行，但首版最多并行两个任务。

### 4.3 审阅 Agent

职责：

- 检查结论是否存在可定位证据；
- 检查数值、单位、币种、期间和同比/环比口径；
- 检查图表理解是否与正文或表格冲突；
- 标记引用错位、证据不足和相互矛盾的结论；
- 决定通过、退回研究 Agent 一次，或以“不确定”状态输出。

审阅 Agent 最多触发一轮返工，防止无限循环。

### 4.4 确定性工具链

以下能力使用普通 Python 函数实现，不交给模型自行决定内部规则：

- PDF 文件校验；
- 页级文本和图片提取；
- 表格抽取与标准化；
- 文本分块和页码映射；
- 证据写入、读取和去重；
- 数值、单位与期间的基础一致性检查；
- 报告模板渲染；
- Token、成本、延迟和异常日志记录。

## 5. 数据流

1. 用户上传 1–3 份 PDF，输入公司、报告期间和研究问题。
2. 系统验证文件类型、大小和页数，并计算文件哈希避免重复解析。
3. 文档解析器按页提取正文、表格和图片，保留原始页码和来源文件名。
4. 解析结果写入本地工作目录和 SQLite 元数据表。
5. 规划 Agent 生成 3–6 个有界 TODO，用户确认研究范围。
6. 研究 Agent 为每个 TODO 检索正文/表格，必要时分析相关图表。
7. 每个候选结论必须写成结构化 `Claim`，并绑定一个或多个 `Evidence`。
8. 审阅 Agent 检查证据和口径；不通过的结论最多返工一次。
9. 通过的结论由确定性模板组织为 Markdown 和 JSON 报告。
10. 用户在发布前查看证据和不确定项，并决定是否接受报告。

## 6. 核心数据结构

### 6.1 Document

- `document_id`
- `filename`
- `sha256`
- `company`
- `report_period`
- `page_count`
- `parse_status`

### 6.2 Evidence

- `evidence_id`
- `document_id`
- `page_number`
- `modality`：`text`、`table` 或 `chart`
- `content`
- `locator`：段落、表格或图片位置
- `extraction_method`

### 6.3 Claim

- `claim_id`
- `claim_text`
- `claim_type`：事实、比较、风险或不确定性
- `evidence_ids`
- `review_status`
- `review_notes`
- `confidence`：仅表示证据充分程度，不表示投资确定性

### 6.4 Run

- `run_id`
- `question`
- `todos`
- `status`
- `started_at` / `finished_at`
- `model_calls`
- `input_tokens` / `output_tokens`
- `estimated_cost`
- `errors`

## 7. 多模态处理原则

### 7.1 数值来源优先级

数值证据采用固定优先级：

1. 结构化表格；
2. 正文明确披露；
3. 图表视觉估算。

首版图表能力主要识别标题、坐标含义、总体趋势、拐点和异常，不从低分辨率图表中输出未经其他来源验证的精确数值。

### 7.2 图表结论规则

- 图表必须保留原始页码和图片编号；
- 图表结论必须标注为视觉理解结果；
- 涉及精确数值时，必须在正文或表格中找到第二证据；
- 图表与正文冲突时，不自动选择其一，交给审阅 Agent 标记冲突；
- 无法识别标题、单位或图例时，输出“不确定”，不得猜测。

## 8. 安全边界与错误处理

### 8.1 不可信文档

PDF 中的所有文字都视为数据而非指令。系统提示明确禁止执行文档内要求改变角色、泄露配置或调用无关工具的内容。工具调用使用白名单，首版不开放 Shell、文件任意路径或外部写操作。

### 8.2 输入错误

- 非 PDF、加密 PDF、空文件或超限文件：解析前拒绝并返回明确原因；
- 扫描件或文本覆盖率过低：标记为首版不支持，建议更换文本型 PDF；
- 缺少公司、期间或问题范围：规划阶段要求补充，不启动昂贵分析。

### 8.3 解析错误

- 单页解析失败不终止整个文档；记录页码并继续；
- 表格抽取失败时保留页面文本和截图，但不得假装获得结构化数据；
- 图像模型失败时降级为纯文本/表格分析；
- 每个外部模型调用设置超时、至多两次指数退避重试。

### 8.4 Agent 错误

- 规划 TODO 超过 6 个时自动要求精简；
- 单次运行设置最大 Agent 步骤和预算；
- 审阅最多退回一次，第二次仍失败则输出不确定项；
- 运行状态持久化，可从最近检查点恢复；
- 最终报告不包含没有证据 ID 的重要结论。

## 9. 技术方案

- Python 3.11；
- `uv` 管理环境与依赖；
- LangGraph/Deep Agents 实现状态、工具调用和子 Agent；
- Pydantic 定义结构化输入输出；
- PyMuPDF 提取页级正文和图片；
- `pdfplumber` 作为首版表格抽取方案；
- SQLite 保存运行、文档、证据和结论元数据；
- 本地文件系统保存解析产物、图片和报告；
- Streamlit 提供纯 Python Web 界面；
- `pytest`、Ruff 和类型检查保障代码质量；
- 模型通过适配层配置，业务代码不硬编码供应商；
- API 密钥仅从环境变量读取，不进入 Git。

## 10. 界面范围

Streamlit 首版只包含三个页面或步骤：

1. **上传与提问**：选择 PDF，填写公司、期间和研究问题；
2. **运行进度**：展示 TODO、当前步骤、失败/重试和预算；
3. **报告与证据**：显示结论、风险、不确定项，并可展开查看页码和原文。

界面服务于演示和可解释性，不追求复杂视觉设计。

## 11. 测试与评测

### 11.1 自动化测试

- 单元测试：文件校验、页码映射、证据去重、数值规范化、报告渲染；
- 集成测试：使用固定小型 PDF 验证解析到 Claim 的流程；
- Agent 合约测试：模型输出缺字段、错误页码或无证据时必须拒绝；
- 端到端测试：上传样本文档并生成可定位证据的报告；
- 回归测试：每次修改 Prompt 或工作流后运行固定评测集。

### 11.2 评测集

使用 3–5 家公开公司、至少 6 份公开报告，人工编写 30 个问题：

- 10 个正文事实问题；
- 10 个表格与财务指标问题；
- 5 个图表趋势问题；
- 5 个风险、冲突或证据不足问题。

### 11.3 核心指标

- **证据覆盖率**：重要结论中绑定有效证据的比例；
- **引用定位正确率**：抽查引用是否能在对应文件和页码找到；
- **数值准确率**：金额、比例、期间和单位是否正确；
- **不确定性识别率**：证据不足时是否拒绝猜测；
- **任务完成率**：是否在步骤和预算限制内产生合格报告；
- **成本与延迟**：每次运行的 Token、估算费用和总耗时。

首版验收目标：30 个问题全部可重复执行；证据覆盖率不低于 95%；引用定位正确率和数值准确率不低于 90%；无证据的重要结论为零。指标未达到时优先修复检索、数据结构和审阅规则，不通过堆叠更多 Agent 掩盖问题。

## 12. Git 学习与协作规范

Git 学习贯穿 12 周，不单独留到项目结束。每次学习都先检查工作区，修改后查看差异，验证通过后再提交。

### 12.1 学习顺序

1. 仓库与工作区：`git init`、`git clone`、`git status`、`git diff`；
2. 创建提交：`git add`、`git commit`、`git log`、`git show`；
3. 忽略文件：使用 `.gitignore` 排除 `.env`、模型缓存、上传文档和运行产物；
4. 安全恢复：区分工作区、暂存区和提交，学习恢复单个文件，不使用破坏性的强制重置；
5. 分支开发：使用 `feature/...` 分支完成一个有边界的功能，再合并回主分支；
6. 远程协作：Fork、添加远程仓库、Push、Pull、处理简单冲突；
7. Pull Request：用问题背景、改动说明、测试证据和截图描述一次改造；
8. 发布作品：创建版本标签和 Release，并附演示与评测结果。

### 12.2 提交原则

- 每个提交只表达一个可以解释的行为变化；
- 提交前运行与改动相关的测试或检查；
- 提交信息说明“做了什么及为什么”，不使用 `update`、`fix stuff` 等模糊文字；
- 不提交 API Key、`.env`、私有或受限数据、大型模型文件和生成缓存；
- 不为了制造提交数量而拆分无意义提交；
- 学习实验和最终项目分别保留清晰历史。

### 12.3 建议提交示例

```text
feat(parser): preserve PDF page numbers in evidence records
test(review): reject claims without source evidence
fix(chart): fall back to text analysis when vision times out
docs(eval): record baseline citation accuracy
```

### 12.4 Git 验收标准

- 能解释工作区、暂存区、本地仓库和远程仓库的区别；
- 能根据 `git diff` 判断本次提交是否包含无关修改；
- 能从一个错误修改中恢复单个文件或创建反向提交；
- 至少通过两个功能分支完成开发；
- 至少创建一份结构完整的 Pull Request；
- Git 历史能够对应 12 周的学习和功能演进，而不是最后一次性上传全部代码。

## 13. 里程碑

1. 完成 5 个学习实验，并能解释其输入、状态、工具和停止条件；
2. 建立独立金融项目，完成 PDF 解析和证据数据结构；
3. 实现规划、研究、审阅三角色闭环；
4. 加入图表理解、证据优先级和失败降级；
5. 完成 Streamlit 界面、运行持久化和恢复；
6. 建立 30 题评测集并形成优化前后对比；
7. 使用功能分支、Pull Request 和可读提交历史记录关键改造；
8. 完成 Docker/启动脚本、README、架构图和演示视频；
9. 根据真实评测数据撰写简历描述并创建项目 Release。

## 14. 成功标准

项目完成时，用户应能够：

- 用一条命令启动应用；
- 上传公开财务 PDF 并提出有边界的问题；
- 看见 Agent 的计划和当前进度；
- 获得带来源文件、页码和证据类型的报告；
- 识别哪些内容是事实、视觉分析或不确定项；
- 查看一次运行的成本、延迟和失败记录；
- 使用固定评测集复现 README 中的结果；
- 从 Git 历史看见项目由实验、MVP、评测到发布的演进过程。

开发者应能够在面试中清楚解释：为什么使用 Agent、为什么只有三个 Agent、哪些步骤必须确定性执行、如何防止图表幻觉和文档提示注入，以及评测指标如何证明改造有效。
